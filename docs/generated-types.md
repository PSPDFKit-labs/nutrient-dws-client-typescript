# Generated types

Everything under `src/generated/` is emitted by [`openapi-typescript`](https://openapi-ts.dev)
from the vendored OpenAPI specs at the repo root.

| File | Regenerated by | From |
| --- | --- | --- |
| `src/generated/api-types.ts` | `npm run generate:types` | `dws-api-spec.yml` |
| `src/generated/extract-types.ts` | `npm run generate:types:extract` | `dws-data-extraction-spec.yml` |

## Changing an API type

1. Update the vendored spec — edit it directly, or replace it with a newer upstream spec.
2. Re-run the relevant generate script.
3. Commit the spec change and the regenerated output together, as one change.

If the regenerated shape is still wrong — missing property, wrong nullability, wrong required
set — the fix belongs in the spec or in a codegen flag. Never in the generated `.ts` file.
A hand-edit is overwritten by the next regeneration and fails CI in the meantime.

## What CI actually enforces

The `generated-types-drift` job in `.github/workflows/ci.yml` runs both generate commands with
`--check` on every PR and fails if the working tree would change. It catches both directions:
a hand-edited generated file, and a spec change that was not regenerated. The `build` job
`needs` it, so a drift failure blocks `build` within that run.

It is **not** currently a merge gate: branch protection on `main` lists no required status
checks, so a red run has to be noticed by a reviewer. Adding `generated-types-drift` to the
required checks in the repository's branch-protection settings would close that gap.

## The two codegen flags are load-bearing

`generate:types` passes two non-default flags:

```
--empty-objects-unknown --default-non-nullable=false
```

Dropping both reintroduces **35** TypeScript errors. They are not equally weighted — measured
with `openapi-typescript` 7.10.1 against the current `dws-api-spec.yml`, by regenerating and
running `npx tsc --noEmit`:

| Flags passed | `tsc` errors |
| --- | --- |
| both (current) | 0 |
| `--empty-objects-unknown` only | 27 |
| `--default-non-nullable=false` only | 8 |
| neither | 35 |

**`--default-non-nullable=false`** — many schema properties declare a `default:`.
openapi-typescript otherwise treats a property with a `default` as always present and emits it
as required. Server responses do not guarantee that, and request bodies certainly do not. This
flag turns the inference off. It accounts for 27 of the 35 errors, because `default:` appears on
far more properties than the pattern below.

**`--empty-objects-unknown`** — the spec uses `allOf: [$ref, {description}]` in several places:
a `$ref` merged with nothing but a sibling `description`. Without the flag, openapi-typescript
renders that as `Record<string, never> & X`, and intersecting with `Record<string, never>`
collapses every property of `X` to `never`. The flag reads an empty object schema in an `allOf`
as "no additional constraints" rather than "no properties allowed."

### Why this warning exists

An earlier version of this repository was missing these flags. Rather than fix the flags, the
generated file was hand-patched to work around the resulting type errors. The patch then
diverged from what `generate:types` produced — silently, for months, because nothing checked.
By the time it was found, running the generate script on a clean checkout produced 23 errors.

That is the whole reason this document and the CI job exist. Do not re-open it by "cleaning up"
the flags.

## Known limitation: watermark dimensions

The spec widened `WatermarkDimension` to `number | string | { value, unit }`, but composes each
watermark dimension slot as `allOf: [{type: object, description}, $ref]`. The object constraint
and the scalar forms contradict each other, and the generator renders the contradiction
faithfully as `Record<string, unknown> & WatermarkDimension`. The scalar shorthand
(`width: 100`) is therefore unusable; the `{ value, unit }` object form works and is unaffected.

Note the causation: `--empty-objects-unknown` is not the culprit. Without it the same slots
degrade further and even the object form stops compiling.

## Where hand-written types are legitimate

`src/types/http.ts` holds hand-written types for shapes the spec genuinely cannot express — not
for shapes that are merely awkward to consume.

The worked example is the `/extraction/parse` block in that file (`ParseOutputOptions`,
`ParseInstructions`, `ParseOptions`, `ParseResponse`). The spec marks `OutputOptions.includeWords`
as required when the server actually defaults it, and the success response is a cross-field
discriminated union the spec does not encode structurally. Both are spec limitations, documented
inline at the point of definition.

The bar is "the spec cannot express this," not "the generated type is annoying." For ergonomics,
derive an alias from the generated `components`/`operations` types instead — see `AccountInfo`,
`AccountUsage`, and `ProductName` in the same file.
